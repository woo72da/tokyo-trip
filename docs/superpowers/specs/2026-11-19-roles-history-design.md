# 역할·개인 기록·변경 기록·날짜 맡기기 — 설계

작성 2026-11-19 · 대상: 서버 버전(v302 이후) · 관련: `docs/12-trip-mates.md`(travel-app-native), `supabase/migrations/0001~0003`

## 1. 왜 (사용자의 말)
- 일행과 같이 갈 때 대부분 **한 명이 짜고 나머지는 보면서 따라간다.** 연인끼리도 그렇다 → '보기만'이 필요하다(다른 서비스도 다 있다).
- 보기만이라도 **방문 장소 리뷰·평가는 사람마다 다르니** 각자 남길 수 있어야 한다.
- **경비는 일정 권한이 없어도 갑자기 쓸 수 있다.** 등록하면 그 사람이 쓴 돈으로 남으니 오히려 좋다.
- 여럿이 편집하면 **갑자기 일정이 바뀌어도 누가 고쳤는지 모른다** → 변경 기록(히스토리)이 있어야 한다.
- 여행 마스터가 짜되, **일부 날짜는 다른 사람이 맡아서** 짤 수 있어야 한다.
- 권한은 **서버에서도 지킨다**(방법 A, 사용자 선택). 앱 화면만 막는 방법(B)은 옛 버전 앱·버그로 뚫리고 리뷰 덮어쓰기도 남아서 뺐다.

## 2. 목표 / 하지 않을 것 / 실패로 보는 것
**목표**
1. 역할 3개: 여행 마스터(owner) · 함께 편집(editor, 맡은 날짜만) · 보기만(viewer).
2. 리뷰·평가·경비는 사람마다 따로 저장(덮어쓰기 없음). 보기만도 자기 것은 쓴다.
3. 누가·언제·무엇을 바꿨는지 보이는 변경 기록 + 마스터의 되돌리기.
4. 마스터가 함께 편집하는 사람에게 날짜를 맡긴다.

**하지 않을 것**
- 집에 있는 가족용 '일정 보기 링크'(가입 없이 보기, 예약번호 숨김) — 따로 나중에.
- 위치 공유·실시간 위치 지켜보기(위치는 폰 안에서만 원칙).
- 보기만에게 예약번호·문서 숨기기 — 기존 결정 유지(보기만도 보임).
- 같은 날 일정을 두 사람이 동시에 고칠 때의 실시간 잠금.

**실패로 보는 것 (돌아가도 안 되는 것)**
- 지금까지 쌓인 경비·리뷰가 하나라도 사라지거나 정산 금액이 바뀌는 것.
- 업데이트 안 한 옛 버전 폰이 계속 '서버와 맞추지 못했어요'로 멈추는 것.
- 보기만인 사람이 화면에서 누를 수 있는데 서버가 거절해서 조용히 사라지는 것(누를 수 없게 숨기거나, 누르면 이유를 알려 줌).
- 남의 리뷰·경비를 내 이름으로 덮어쓰는 것.

## 3. 지금 구조 (조사 결과)
- 함께 쓰는 기록은 `trip_kv(trip_id, key, value, updated_at, updated_by)` 한 줄 = 키 하나. 예약번호류는 `trip_secrets`. 폰에서는 `store.set(key)` → `isShared(key)`면 `meta[key]` 시각 기록 → `cloudSync`가 upsert. 값이 null이면 지운 것.
- 목록 키(`MERGED_LISTS`: custom, cdocs, exp, myitems, myplaces)는 **목록 전체가 키 하나**이고 id로 합친다.
- **경비 `exp`는 모든 사람의 경비가 한 줄**(각 항목에 `by` = 계정 id). **리뷰 `visit:<장소id>`는 장소마다 한 줄**(`by`, `memo`, `again` 평가) → 두 사람이 같은 장소를 평가하면 나중 것이 덮어쓴다(현재 버그).
- `gear:<날짜>:<계정id>`는 이미 사람별.
- 서버 권한: `is_member`(읽기) / `can_edit` = owner·editor(쓰기) / `is_owner`. `trip_members.role`은 이미 'viewer'를 받는다. `members_update`는 owner만. 초대(`trip_invites.role`, 기본 'editor')로 들어오면 그 역할.
- 사진은 비공개 버킷 `docs/<tripId>/<이름>`, 쓰기·지우기는 `can_edit`.
- 앱: `CLOUD.role`이 있고, viewer면 일정 파일 올리기·사진 올리기만 건너뜀. 수정 버튼은 숨기지 않음.

## 4. 접근 방법 (고려한 것)
| 방법 | 내용 | 판단 |
|---|---|---|
| **A. 사람별 저장 + 서버 규칙 (선택)** | 개인 기록을 계정 id가 붙은 키로 나누고, 서버가 "보기만은 내 id가 붙은 키만 쓰기"를 지킨다 | 버그·옛 앱에도 안전, 덮어쓰기 해결, 변경 기록과 잘 맞음. SQL 1회 + 기존 기록 옮기기 필요 |
| B. 앱 화면에서만 막기 | 버튼만 숨김 | 빠르지만 서버가 다 허용, 덮어쓰기 남음 → 뺌 |
| C. 서버 함수(RPC)로만 쓰기 | 모든 쓰기를 검사 함수로 | 가장 엄격하지만 지금 동기화 구조를 다 바꿔야 함 → 과함 |

**날짜 맡기기는 앱에서 지키고 서버는 '함께 편집이면 일정 쓰기 가능'까지만 본다.** 일정 수정 키(`edit:<일정id>` 등)에 날짜가 들어 있지 않아 서버가 날짜를 알 수 없고, 친한 일행 사이라 변경 기록으로 누가 고쳤는지 보이면 충분하다고 판단(빌더 판단 아님, 설계 결정).

## 5. 설계

### 5-1. 기록 분류 (키 → 누가 쓰나)
| 분류 | 키 | 마스터 | 함께 편집 | 보기만 |
|---|---|---|---|---|
| 개인 | `exp:<uid>`(내 경비 목록), `visit:<장소id>:<uid>`(내 리뷰·평가), `gear:<날짜>:<uid>`, `prep:<날짜>:<uid>`, `tomb:<uid>`(내가 지운 것 표시) | 내 것 | 내 것 | 내 것 |
| 일정 | `edit:*`, `custom`, `myitems`, `myplaces`, `start:*`, `done:*`, `seal:*`, `save:*`, `ck:*`, `route:*`, `budget`, `cashYen`, `nick:*` 등 나머지 공유 키 | ○ | ○ (앱: 맡은 날짜만) | ✕ |
| 예약·문서 | `trip_secrets` 전부(pnr, agoda, esim, cdocs) | ○ | ○ | 읽기만 |
| 사진 | 경비 영수증 사진(내 경비에 딸린 것) | ○ | ○ | 내 것 |
| 사진 | 그 밖의 문서·바우처 사진 | ○ | ○ | 읽기만 |

- 개인 키는 **끝이 `:<내 계정 id>`인 키**로 통일한다(`exp:<uid>`도 끝이 uid). 서버 규칙은 이 모양 하나로 판단.
- `prep`(아침 준비 체크)는 사람마다 챙길 게 달라서 개인으로 옮긴다. `diary:<날짜>`·`diary:trip`(AI 여행 일기)은 공유 일정 기록으로 만든 '우리 여행 이야기'라 **공유 유지**(일정 키, 마스터·편집자가 만듦).
- 남의 개인 키는 누구도 쓸 수 없다(마스터 포함). 단, 여행 삭제·내보내기 때 DB가 지우는 건 예외.

### 5-2. 서버 (SQL `0004_roles_history.sql`, 사용자가 SQL Editor에서 실행)
1. **개인 키 함수** `is_own_key(key text) returns boolean` = `key like '%:' || auth.uid()::text`.
2. **trip_kv 쓰기 규칙 교체**: insert/update/delete 모두 `can_edit(trip_id) and not is_others_personal(key)` **또는** `is_member(trip_id) and is_own_key(key)`.
   - `is_others_personal(key)`: 개인 키 모양(`exp:`, `visit:*:`, `gear:`, `diary:*:`, `prep:*:`로 시작하고 끝이 uuid)인데 내 id가 아닌 것 → 편집자도 남의 개인 기록은 못 씀.
3. **사진 규칙**: 쓰기·지우기에 "멤버이고 파일 이름에 내 계정 id가 들어간 경비 영수증" 허용을 추가. 영수증 사진 이름 규칙을 앱에서 `rcpt:<경비id>:<uid>…`처럼 uid를 포함하도록 바꾼다(정확한 이름 형식은 빌더가 현재 `docName`을 보고 정함).
4. **맡은 날짜**: `trip_members.days date[]` 추가(null = 모든 날). 마스터만 바꿈(기존 `members_update`).
5. **변경 기록 표** `trip_log(id, trip_id, key, old jsonb, new jsonb, by uuid, at timestamptz)` + `trip_kv`·`trip_secrets`의 insert/update 트리거로 자동 기록. 읽기 = 멤버, 쓰기 = 트리거만. 오래된 기록은 여행당 최근 2000건 또는 90일만 남김(트리거나 주기 정리, 빌더 선택). `route:*` 같은 계산 캐시 키는 기록하지 않음.
   - `trip_secrets`의 값(예약번호)은 기록에 **값을 남기지 않고** "예약번호를 바꿨어요"만 남긴다(old/new = null).
6. **기존 기록 옮기기(같은 SQL 안, 한 번만, 다시 실행해도 안전하게)**
   - `exp` 한 줄 → 항목의 `by`별로 `exp:<by>` 줄로 나눔. `by`가 uuid가 아닌 옛 값('me', '나', '안드레아')은 여행 주인 uid로.
   - `visit:<장소id>` → `visit:<장소id>:<by>`(같은 규칙).
   - `prep:<날짜>` → 여행 주인 uid로 옮김. `diary`는 그대로.
   - 옮긴 옛 키는 지우지 않고 값만 null로(다른 폰에 '지움'이 전달되게).
   - 옮기기 전후 경비 합계가 같은지 SQL 마지막에 확인해 보여 준다.
7. **초대 기본 역할을 '보기만'으로**: `trip_invites.role` 기본값 'viewer'. 이미 있는 링크는 그대로. 이미 들어온 사람은 지금 역할(함께 편집, 모든 날) 유지.

### 5-3. 앱
- **읽기 모델**: 경비 = 모든 `exp:*` 목록을 합친 것(`expenses()`가 합쳐서 돌려줌). 리뷰 = 장소별로 `visit:<id>:*`를 모아 사람별로 보여 줌, 평가 집계는 사람 수로. 내 것만 수정·삭제 가능.
- **쓰기 모델**: 내 경비 추가·수정·삭제는 `exp:<내 uid>`만. 리뷰는 `visit:<id>:<내 uid>`만.
- **옛 키 호환(업데이트 안 한 폰 대비)**: 새 앱은 옛 `exp`·`visit:<id>`·`diary:<날짜>`·`prep:<날짜>` 값이 들어오면(옛 폰이 썼을 때) 위와 같은 규칙으로 개인 키로 옮겨 쓰고 옛 키를 null로 보낸다. 옛 앱은 새 키를 모르므로 경비가 덜 보일 수 있다 → 앱을 열 때 '새 버전으로 업데이트해 주세요' 안내(버전 확인은 기존 `loadLatest` 방식).
- **권한 가드 한 곳**: `canWrite(key)` = 개인 키면 내 것인지, 일정 키면 role이 owner/editor이고(editor면) 그 키의 날짜가 맡은 날짜인지. `store.set`과 수정 버튼 그리기에서 같이 씀. 보기만·맡지 않은 날에는 수정 버튼을 숨기고, 그래도 들어온 쓰기는 막고 "이 날은 ○○님이 짜는 날이에요" / "보기만 권한이에요" 알림.
  - 일정 키의 날짜: `edit:<일정id>`·`done:`·`start:`는 일정id로 그 날을 찾고(`state.trip.days`·`myitems.date`), `seal:<날짜>`는 그대로, 날짜를 알 수 없는 일정 키(`custom`, `myplaces`, `save:`, `ck:`, `budget`, `cashYen`)는 **마스터와 모든 날을 맡은 편집자만**.
- **역할·날짜 관리 화면**(설정 › 여행 › 함께하는 사람 › 관리): 권한 [함께 편집 | 보기만], 함께 편집이면 맡은 날짜 고르기(모든 날 / 날짜 여러 개). 본인(마스터)은 바꿀 수 없음.
- **초대 카드·참여 후 안내**에 들어올 권한을 보여 줌("보기만으로 들어가요. 리뷰와 경비는 쓸 수 있어요").
- **일정 화면 날짜 머리**에 맡은 사람 표시(예: "3일차 · 다희님이 짜요").
- **변경 기록 화면**(설정 › 여행 › 변경 기록, 모든 멤버가 봄): 최근 순, "다희님 · 11/20 14:03 · 3일차 점심 시간을 12:00→12:30으로". 키별 사람이 읽는 문장 만들기는 일정·경비·리뷰·예약 위주로, 나머지는 "기록을 바꿨어요". 마스터에게만 일정 기록 옆 **되돌리기**(그 키를 old 값으로 다시 씀 → 그것도 기록에 남음). 개인 기록은 되돌리기 없음.
- 문구는 해요체, 버튼은 DESIGN.md 규칙(진한 버튼 하나, 지우기는 빨간 테두리).

### 5-4. 배포 순서 (옛 폰 보호)
1. 앱 v-A: 새 키 읽기(옛 키도 계속 읽음) + 옛 키 → 새 키 옮겨 쓰기, 권한 가드는 아직 끔. **SQL 전에 배포해도 지금처럼 동작**해야 함.
2. 사용자 SQL 실행(0004).
3. 앱 v-B: 권한 가드·관리 화면·변경 기록 화면 켜기.
각 단계는 요청함 규칙대로 SQL 실행 확인 뒤 다음 배포.

## 6. 빌더에게 맡기는 것
- 테이블·함수·트리거 이름 세부, 로그 정리 방식(트리거 vs 주기), 영수증 사진 이름 형식.
- 변경 기록 문장 만들기의 세부 문구(해요체 유지).
- 관리 화면 레이아웃 세부(DESIGN.md 따름).

## 7. 결정한 것 중 사용자 확인이 필요한 것 (설계 승인 때 함께)
- 새로 초대받는 사람의 기본 역할 = 보기만.
- 아침 준비 체크는 사람별, AI 여행 일기는 함께 쓰는 하나로 유지.
- 날짜 맡기기는 앱에서만 지킴(서버는 편집자면 일정 쓰기 허용), 대신 변경 기록으로 누가 고쳤는지 보임.
- 변경 기록은 모든 멤버가 보고, 되돌리기는 마스터만.
- 예약번호는 기록에 값 없이 "바꿨어요"만.

## 8. 검토(빌더 체크) 반영 — 결정 사항
1. **지운 표시(`tomb`)**: 지금은 모두가 같이 쓰는 키 하나라 보기만이 내 경비를 지우면 서버가 거절한다 → `tomb:<uid>` 개인 키로 나누고, 읽을 때는 모든 `tomb:*`를 합친다. 옛 `tomb`은 읽기만 하고 더 쓰지 않는다.
2. **서버가 거절한 쓰기**: 보내기 전에 `canWrite(key)`로 걸러서 내가 쓸 수 없는 키는 보내지 않는다. 그래도 거절되면(역할이 막 바뀐 경우) 그 묶음을 한 줄씩 다시 보내 거절된 키만 이 폰에서 서버 값으로 되돌리고 "권한이 바뀌어 일부 변경은 반영되지 않았어요" 알림. 동기화 전체가 멈추지 않게 한다.
3. **옛 기록의 '누가'(by)**: 항목 안의 `by` 값은 **절대 바꾸지 않는다**(정산은 `by`로 묶으므로 그대로 유지). 옮기기에서 정하는 건 "어느 줄(`exp:<uid>`)에 넣느냐"뿐: `by`가 멤버 uid면 그 사람 줄, 아니면('me'·'나'·'안드레아'·'다희'·'와이프' 등) 여행 주인 줄. 그래서 정산 금액과 '누가 냈나'가 그대로다. SQL 확인은 합계뿐 아니라 `by`별 합계 전후 비교.
4. **날짜 맡은 편집자의 일정 추가**: `myitems`는 서버에서 편집자에게 열어 두고(날짜 지키기는 앱 몫), 앱이 항목의 `date`가 맡은 날짜인지 본다. `custom`(체크리스트 메모)과 `myplaces`·`save:`·`ck:`·`budget`·`cashYen`처럼 날짜가 없는 키는 마스터·모든 날 편집자만.
5. **되돌리기 범위**: 값 하나짜리 키(`edit:`, `done:`, `start:`, `seal:`, `budget` 등)만 되돌리기 제공. 목록 키(`myitems`, `myplaces`, `custom`)는 기록만 보이고 되돌리기 없음. 되돌리기는 지금 시각으로 다시 쓴다(옛 시각으로 쓰면 다른 폰이 무시함).
6. **리뷰 주인 정하기(옮기기)**: `visit:<장소id>`는 `trip_kv.updated_by`(마지막으로 메모·평가를 쓴 계정)를 우선, 없으면 항목의 `by`, 그것도 uuid가 아니면 여행 주인.
7. **개인 키 판별**: `like '%:' || uid`로 판단하지 않고, 정해진 앞부분(`exp:`, `visit:`, `gear:`, `prep:`, `tomb:`) + 끝이 내 uid인 경우만 개인 키로 본다.
8. **`trips.plan` 올리기**: 도쿄 여행에서 앱 파일을 서버로 올리는 자동 동작(사람의 수정이 아님)이라 변경 기록·날짜 검사 대상이 아니다. 마스터 폰만 올리도록 바꾼다(지금은 보기만이 아닌 모두).
9. **§3 정정**: 지금 보기만이 건너뛰는 건 `trips.plan` 올리기, 사진 올리기, 서버 사진 지우기 세 가지다.
